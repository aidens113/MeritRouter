# Approval wait versus execution timeout

## Cause
executeOperation started a wall-clock operation timer before the declared check filed an exact worker-action request. Human approval waiting consumed that timer. On expiry the operation signal cancelled the pending request; the worker could continue, change source and file a replacement before the user approved the stale row.

## Changes
- harness/operation-lifecycle.ts separates the active-work timeout from a hard, unpaused task-deadline timer. Internal clocks can pause only through a runtime function, never through a model tool. Pauses propagate through parent operation signals, so grouped checks inside a batch do not retain an expiring ancestor timer while approval is pending. Reference counts protect shared ancestor clocks. Settled/aborted clocks are not restarted, and a spent active budget aborts immediately even if its timer callback was delayed.
- harness/worker-actions.ts suspends these active clocks only after validating the stored pending request against the current task and captured lease. It resumes when the request runs or resolves, and always releases the pause in finally. Existing task deadline, explicit cancellation, lease authority, source identity and broker policy checks remain active. Operator runProcess respects its requested timeout and any stricter captured active ancestor cap; cancellation waits for confirmed process quiescence.
- Source capture remains active preflight, not a paused phase. Cancellation is checked before capture and again after its asynchronous hash immediately before persistence/current-lease revalidation; cancelled capture cannot create a late pending row.
- harness/recipe-operations.ts descriptions distinguish bounded active work from pending approval wait and explicitly preserve source preflight/task deadlines/cancellation.
- tests/external-task-tools.test.ts changes the old approval-wallclock-expiry assertion into an explicit cancellation test: the request remains pending beyond its execution timeout, then caller cancellation retires it; late approval still cannot execute it. Existing real-MCP execution-timeout/quiescence assertions remain intact.

## Limits
Waiting is bounded by task deadline/lease and explicit cancellation, not the requested command-execution timeout. Active preflight and post-execution bookkeeping still consume the operation's active-work budget; each actual command also retains its own requested process timeout. No stale approval is transferred to a changed source, and no operator approval is generated by this change. Root owns independent integrated validation, deployment and live product acceptance.

## Follow-up: execution between polls and hard ancestor cap
Root review found that an operator can approve and complete a fast command between100ms waiter polls. Merely resuming the execution timer on the next observed status would exclude that actual work from a grouped/batch active budget.

WorkerActionRequest now permits two optional runtime-owned JSON fields (no SQL migration): executionStartedAt is written from server Date.now in the atomic execution claim, and executionTimeoutMs is the minimum requested limit and remaining active operation/ancestor budget captured after source hashing. Decider runProcess enforces min(action.timeoutMs, executionTimeoutMs); legacy rows retain their requested limit when the optional cap is absent.

The requested action/timeout and request key remain stable. Dynamic cap metadata is outside that key, so same invocation/source replay returns the same approval ID and can only narrow its effective cap. Expired/empty active remainder aborts/refuses filing without a pending row.

When a pending wait observes running/completed/uncertain, releasing its pause charges all elapsed time since trusted executionStartedAt before restarting active timers. Missing legacy start timestamps conservatively charge the whole paused span. Overlapping ancestor pause charges merge intervals rather than double-counting. Exhausted budgets abort synchronously, preventing the next grouped command from being filed before a deferred timeout callback.

Added actual grouped-command fast-completion regressions with operator completion before the first waiter poll (normal and legacy timestamp rows), an independent broker cap/process-kill test after both caller clocks already settled, same-ID/narrower-cap replay assertion, and an exact overlapping-interval union regression. Faked timing is restricted to deterministic timer-boundary accounting fixtures; the independent broker cap case restores real timers before actual process execution and proves no delayed write.
