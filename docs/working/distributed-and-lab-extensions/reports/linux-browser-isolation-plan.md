# Native Linux browser isolation plan

Status: report frozen for architecture review; no implementation or hydrated-runtime acceptance.
Date: 2026-10-22. Baseline: cb8359a, feat/linux-browser-isolation-plan.

## Recommendation

Implement an unavailable-by-default native Linux Bubblewrap adapter with a small trusted Python launch/monitor helper, then validate portable Linux Chrome separately. Use the already installed non-setuid `/usr/bin/bwrap`, not Docker, host firewall rules or a new privileged service. Node and broker must run natively in the Linux environment; a Windows process spawning WSL is not automatically this adapter. WSL is the present test host, not a new public Windows backend. H1's static-compatible public unavailable capability remains truthful until the real helper/lease and later Chrome acceptance pass.

Network namespace, private filesystem root, descriptor control, owner-death lifecycle and independently checked kernel identities together form the proposed boundary. A helper JSON statement or nominal lease alone proves none of these. Human-selected trusted executable/helper/runtime paths and the host kernel/admin remain trusted. This does not defend against Docker/root peers, kernel/browser sandbox escapes or arbitrary native executables the human has deliberately authorized. Models still select authored check names; they get no URL/evaluate/script/argv/helper/mount authority.

## Verified platform facts and consequences

Linux network namespaces isolate the IP stack and abstract Unix-socket namespace. Pathname Unix sockets still require filesystem isolation; mounts of host `/run`, home, `/tmp` or WSLg would reopen broker paths. [Network namespaces](https://man7.org/linux/man-pages/man7/network_namespaces.7.html), [Unix sockets](https://man7.org/linux/man-pages/man7/unix.7.html).

Bubblewrap builds an empty filesystem root and supports explicit namespaces/capability/environment policy. Its installed-version source passes extra descriptors to the executed child, so the caller must supply an exact descriptor allowlist. Its `--block-fd` read does not require a byte: EOF also proceeds. It is a setup synchronization aid, not the final authenticated owner gate. [Version0.6.1 manual](https://raw.githubusercontent.com/containers/bubblewrap/v0.6.1/bwrap.xml), [version0.6.1 source](https://raw.githubusercontent.com/containers/bubblewrap/v0.6.1/bubblewrap.c).

PID-namespace init death causes the kernel to SIGKILL its namespace processes. Parent-death signals alone have fork/credential/thread/installation-race caveats; retain a separate owner channel and fail-closed launch gate. [PID namespaces](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html), [PR_SET_PDEATHSIG](https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html).

Seccomp can check syscall arguments, and filters persist through allowed fork/exec. It cannot inspect arbitrary pointed-to socket-path bytes as a pathname policy. no_new_privs prevents gaining privilege through exec; it is not an independent network barrier. [Kernel seccomp contract](https://docs.kernel.org/userspace-api/seccomp_filter.html), [kernel no_new_privs](https://www.kernel.org/doc/html/latest/userspace-api/no_new_privs.html). An architecture-checked additional filter can reject socket domains other than AF_UNIX and deny io_uring/namespace re-entry/FD-stealing operations, but actual Chrome compatibility remains untested. Do not ship a guessed seccomp allowlist or count the observed Seccomp0 probe as a filter test.

## Proposed trusted helper and positive lease

1. Linux-only adapter validates a closed bounded private launch DTO: generated generation/nonce, pinned executable/helper hashes and inode identities, exact profile/artifact directory handles, fixed limits. No free-form argv/environment/mount/path additions. Refuse unsupported kernels/helper versions, symlinked/writable helper ancestry, unknown architecture or Windows/WSL interop executable. First profile targets installed Python3+bwrap, not arbitrary PATH programs. Revalidate executable/fixture bytes against human-approved provenance; never derive trust from the same child attestation being checked.
2. Before any browser exec, write a private checked launch-intent containing owner process birth/boot ID, generation and owned paths. Initial adapter-only prerequisite may use an injected ownership-record port and refuse runtime registration; durable Lab integration is separately owned. Creation ambiguity preserves that record and profile.
3. Owner starts a trusted monitor with an EOF-sensitive owner pipe: only the owner retains its write end, never bwrap/browser. Monitor verifies its expected parent birth and monitors pidfd plus pipe; early EOF exits without launch. All subprocess stdio is explicitly constructed; no tty, inherited socket, repository directory FD, service token, API key, environment agent, proxy, DBus, XDG runtime, DISPLAY/WAYLAND, LD_*, NODE_OPTIONS, WSL_INTEROP or WS launch authority enters the child.
4. Monitor launches bwrap in new user/net/mount/PID/IPC/UTS/cgroup namespaces with --die-with-parent, --new-session, --cap-drop ALL, uid/gid mapped nonzero inside, --clearenv. Do not use namespace *-try, --share-net, host root or --as-pid-1. Keep bwrap's trusted PID1 reaper. Independently check zero caps and no_new_privs after all credential transitions. The root launch used for probes is not the desired production owner account: repeat acceptance as an ordinary Linux account without installing setuid helpers.
5. Build a socket-free private root: approved Chrome tree and only required libraries/fonts/certificate/config regular files read-only; private /proc for the new PID namespace, minimal /dev (no network/tun/host devices), tmpfs /tmp,/run,/dev/shm and private home/profile. No /sys, host /proc, /mnt, /run, whole /etc/home/tmp, agent sockets or Docker endpoint. Validate bind sources by opened identity and reject socket-containing or mutable broad roots. Resolver configuration is a generated fixed regular file, not a symlink into host resolve service. AF_UNIX creation can remain available for Chrome-internal IPC because pathname host sockets are absent and abstract sockets live in the new netns. Optional syscalls strengthen this boundary; deny AF_VSOCK and other families, not merely AF_INET/6. No host portal/session bus or descriptor-transfer service exists inside.
6. The child command is a trusted inner stage, not Chrome directly. It emits bounded nonce-tagged setup metadata over a dedicated one-way pipe, then requires an exact framed release message; EOF, malformed input, timeout or wrong nonce exits. Bwrap --block-fd may assist setup but is insufficient. Bind CDP only to dedicated anonymous pipes FD3/4; map helper handshake/owner channels elsewhere and close them before browser exec. Verify actual FD type/access and closure; Linux Node stdio can be Unix socketpairs, so do not assume every Node 'pipe' is a kernel pipe. Browser must inherit no owner write end. Browser-controlled CDP input never controls helper actions.
7. Outer monitor/adapter independently opens pidfds and proc namespace handles while child is gated: boot ID + start-time + parent/descendant relation + distinct net/user/mount/PID namespace inode sets + expected namespace memberships + approved mount tree and caps/NNP. Compare kernel observations with the private intent and helper handshake. Helper metadata is corroboration, not proof. Proc visibility/ptrace restrictions that prevent this check yield unavailable; do not downgrade to JSON trust. Track bwrap monitor, PID1, inner process and eventual browser birth separately, including expected exec transitions. Namespace descendants may nest further but must remain under the owned outer PID lifetime and cannot gain host namespace FDs.
8. Release trusted inner stage only after owner liveness/intent persistence/kernel proof. It execs pinned Chrome with fixed headless/CDP-pipe flags and its own normal sandbox enabled; never --no-sandbox. There is still no application navigation until H1 CDP negotiation and later H2 guards succeed. A browser/renderer cannot legitimately alter outer ownership proof. assertOwned rechecks pinned process lifetimes/kernel handles/containment before privileged broker effects and final evidence; stale PID alone is never adopted.
9. EOF, cancellation, monitor/owner crash or timeout closes release/CDP channels and kills exact owned PID1 through pidfd, causing descendant cleanup; --die-with-parent is another layer. Wait for pidfd/process termination and namespace references to drain. Only then remove checked owned profile paths and finalize records. An uncertain process/ref/path relationship quarantines and preserves artifacts. Do not claim killing one browser PID empties a namespace. Actual crash tests must cover helper death before bwrap installs its parent-death hook: the unreleased inner gate must prevent browser execution in that window. After release, verify PID1 parent-death chain really kills every descendant; a failed test blocks availability.

Private proc-only proof and user-namespace restrictions need implementation measurement. If pidfd/namespace proof cannot be made reliable using installed Python APIs/ctypes without broad privileges, stop at unavailable and request a separately reviewed small compiled helper; no silent shell/PID fallback. Existing Python3.10 os.pidfd_open works, but Python syscall bindings, FD handoff and signals are not accepted simply because that one call works. Resource caps are separately required against fork/memory abuse; observed cgroup availability is not accepted cgroup ownership/delegation. First adapter prerequisite must remain unavailable for arbitrary browser workloads until bounded process/resource containment is demonstrated.

## Actual acceptance still required

Use an outside-namespace fixture with distinct TCP listeners, UDP/DNS counters and Unix resolver/portal sentinels (filesystem and abstract), all local. First verify positive sentinel reachability from an unisolated controlled client, then require zero accepted foreign contacts from the isolated adversary. Do not start these sentinels from this report-only unit.

Native adversary tests must bypass/disable CDP interception and attempt IPv4/IPv6 loopback, host/private literal addresses, TCP/UDP, DNS, AF_VSOCK, raw/netlink/packet sockets, filesystem+abstract AF_UNIX, inherited socket reuse, SCM_RIGHTS and proc-FD reopening. Unexpected success blocks availability, not just check success. Browser tests then execute fetch/XHR/image/script/redirect/form/beacon/preconnect, WS/EventSource, dedicated/shared worker and service-worker fetches, popup/iframe and WebRTC/STUN/TURN TCP/UDP/WebTransport where actually supported. Unsupported APIs are reported individually, never counted as zero-contact passes. Test fixtures may intentionally relax CSP/interception solely to exercise the OS boundary; product policy stays closed. Host contacts remain zero even when scripts/worker targets race CDP setup.

Also verify actual pipe FD3/4 compatibility, JS delayed DOM mutation through a bounded parent-broker fulfillment, nested descendants, owner SIGKILL during launch/after gate/CDP/navigation/screenshot, helper/bwrap/PID1 deaths, PID reuse, close responsiveness, fake inherited credential/environment sentinels, profile preservation on ambiguous cleanup and deletion only after proven exit. Assert zero surviving descendant births, closed owner/CDP FDs and unchanged user data. Owner-crash tests need an independent ancestor harness with pidfds that stays alive to inspect results. Budget process count/memory/CPU and bounded hard deadlines so an infinite JS or fork attempt cannot hang the host. No cgroup permission or real Chrome success has been established here.
