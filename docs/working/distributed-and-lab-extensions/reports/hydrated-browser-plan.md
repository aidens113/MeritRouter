# Hydrated browser check implementation plan

Status: Ready for architecture review, not implemented or verified. Report-only worker unit; frozen session source untouched.
Date: 2026-10-22

## Recommendation and decision required

Keep explicit `mode: static` unchanged. Implement the next mode as a capability-gated, restricted hydrated DOM check: one declared service origin, scripts enabled, bounded same-origin GET/HEAD resources, declarative DOM readiness/assertions and one screenshot. Require a separately enforced browser-process deny-all network boundary; only the parent resource broker may access the declared owned service. Unsupported hosts return `browser_isolation_unavailable` before application navigation or script execution. Do not silently downgrade to flags/proxy/CDP-only execution or report static rendering as hydration.

The current Windows installation has Chrome 155.0.8059.86 (read executable VersionInfo only). This investigation did not establish an available Windows isolation adapter. The framework can implement schema, broker, evidence, transport and capability-failure paths independently, but enabling hydrated execution requires an actual accepted platform adapter. First recommendation is a Linux namespace adapter on an explicitly provided compatible host; Windows AppContainer support is a separate reviewed native unit. Neither Docker nor an OS service/firewall installation is authorized by this report. No native adapter already exists in the inspected implementation.

Human configuration authorizes executable, mode, origin via service name, limits and assertion names. Models continue selecting only an existing declared check name. There is no model URL, evaluate, JavaScript, CDP, click, form, network-policy or executable argument. This restricts model authority; it does not make an arbitrary human-configured executable or service command safe. Trusted local executables, operating system, owner credentials and service commands remain a host boundary. Arbitrary privileged host peers and browser/OS escape vulnerabilities are outside a claimed network-policy proof.

## Actual implementation contract and insertion points

- `browser-schema.ts:11–44`: strict static-only check/evidence; explicit mode required, three DOM assertion kinds, existing viewport/time/resource/byte/screenshot limits. Preserve old shape and result parsing. Add a strict hydrated branch, not a default mode change.
- `browser-network.ts:17–42,73–122`: validates running service PID/token and allocated IPv4-loopback origin, rechecks owned process/listener before and after parent `fetch`, manually refuses redirects, GET/HEAD only, bounded serialized resources, reconstructs response headers with a script-disabling CSP. Chrome requests are fulfilled; never continue them. Hydrated adds Script/Fetch/XHR resource types through this same authority, not a second network client.
- `browser-check.ts:48–89,92–135,147–201`: root target paused/configured, offline mode, scripts disabled, service workers bypassed, all extra targets closed, exact clean committed heads before/after, DOM assertions and bounded screenshot. Enabling scripts requires a different audited setup state machine, not removing the Emulation call alone. Current console/page-error content is static-mode specific and insufficient for hydrated diagnostics.
- `browser-process.ts:24–119`: fresh private profile, minimal environment, dead-end HTTP proxy, resolver/feature/QUIC/WebRTC flags, tokenized process wrapper, DevTools listener ownership proof and process-tree cleanup. Keep this static path. Hydrated needs a containment launch adapter and pipe CDP; do not inherit the current localhost debug listener assumption.
- `browser-protocol.ts:11–95`: WebSocket CDP, runtime envelopes validated, 12MiB per message, pending calls rejected on close/abort. Add bounded byte-stream framing transport; preserve WebSocket implementation for static. Enforce cumulative bytes/events/in-flight commands too, since per-message limits alone permit an unbounded JS event flood.
- `browser-artifacts.ts`: generated scoped IDs, PNG magic/size/hash checks, checked paths and retrieval integrity. Reuse unchanged unless metadata versioning demands a narrow explicit hunk.
- `checks.ts:13–19,38–41`: result schema and all-heads matching consume evidence. Update via schema compatibility only; no fabricated task/verification acceptance.
- `lab.ts:584–605,647–666`: recovery handles task attempts/services; graceful close aborts/awaits operations. The inspected browser event references do not establish crash recovery of orphaned browser checks. Current Windows proof file includes private token/process identities; it is captured after debugger readiness. Hydrated needs durable launch intent and ownership/containment lifetime before execution, not merely started/closed events.

Read tests: `tests/labs-browser.test.ts` and `tests/fixtures/lab-browser-server.cjs`. They cover actual static Chrome, hydration deliberately failing, foreign redirect/image/preconnect traps, resource limits, port rebound, cancel/startup timeout and artifact integrity. The JavaScript/WebSocket attack fixture currently does not execute because scripts are disabled. Those passing static tests cannot establish hydrated transport containment.

## Verified external facts

1. CDP Fetch Request-stage interception pauses a matching request before sending; fulfill can substitute response bytes. Its documented contract does not establish coverage of every independent browser transport. Use it for brokered requests; never infer a universal network sandbox. [CDP Fetch](https://chromedevtools.github.io/devtools-protocol/tot/Fetch/)
2. Target auto-attach pauses directly related targets and its protocol source explicitly discusses recursive attachment. One root setup is not documented as sufficient coverage of every nested target. [Official Target protocol source](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Target.pdl)
3. Network exposes WebSocket/WebTransport creation notifications, not a documented universally pausing pre-contact gate for them. The existing offline command is deprecated in favor of newer emulation/state commands; emulation documentation is not an OS egress contract. [CDP Network](https://chromedevtools.github.io/devtools-protocol/tot/Network/), [official Network protocol source](https://chromium.googlesource.com/devtools/devtools-frontend/+/main/third_party/blink/public/devtools_protocol/domains/Network.pdl)
4. Chromium has implicit localhost/link-local proxy bypass rules; `<-loopback>` subtracts these rules for manual proxies. This supports the existing flag choice, not transport-wide isolation. [Chromium proxy documentation](https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/proxy.md)
5. CSP defines connect-src for fetch/XHR/EventSource/beacon/ping/WebSocket and worker-src for workers. The current CSP specification also defines a separate WebRTC directive; specification presence does not prove implementation in this installed Chrome. Do not claim connect-src alone covers WebRTC or DNS. [W3C CSP](https://www.w3.org/TR/CSP/)
6. `disable_non_proxied_udp` is an actual Chromium policy value. Historical Chromium analysis explicitly distinguishes TCP TURN behavior. It is not an all-WebRTC-off guarantee, and historical issue evidence is not a current exploit reproduction. [Chromium policy constants](https://chromium.googlesource.com/chromium/src/+/ee3e1d2a538f5659c3ad887ea5de95d31b9c8a72/content/public/common/webrtc_ip_handling_policy.cc), [Chromium issue analysis](https://bugs.chromium.org/p/chromium/issues/detail?id=767304)
7. Chromium supports remote debugging pipe. Official source writes/reads NUL-delimited JSON in its default ASCIIZ mode; the launch change documents descriptors 3 and 4. The product must bound its own framing buffer rather than adopt Chromium's much larger internal receive allowance. [Chromium pipe implementation](https://chromium.googlesource.com/chromium/src/+/main/content/browser/devtools/devtools_pipe_handler.cc), [descriptor validation change](https://chromium.googlesource.com/chromium/src/+/e972c575b9a075ab5dcadddf269d60bb23d4af35)
8. Linux network namespaces isolate IP stacks/devices/routes/ports; namespace creation has kernel/capability constraints and can fail. Windows AppContainer offers separately allocated network capabilities. These are candidate primitives, not tested SwitchYard adapters. [Linux namespace contract](https://man7.org/linux/man-pages/man7/network_namespaces.7.html), [unshare requirements](https://man7.org/linux/man-pages/man2/unshare.2.html), [Microsoft AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)

## Before-contact transport policy

The hard boundary must already hold when the browser process starts, including browser/network-service descendants before CDP attaches. Do not rely on observing and then closing a connection. The parent broker remains outside that boundary with narrowly scoped service authority.

| Surface | First hydrated subset and enforcement |
|---|---|
| Fetch/XHR, scripts/modules, CSS/images/fonts | CDP Request-stage broker: exact canonical `http://127.0.0.1:allocatedPort` origin, GET/HEAD only; no credentials or browser-supplied headers/body; resource and total byte caps; fresh ownership checks; no browser direct network. Deny foreign before parent fetch. |
| Redirects, forms, beacons, ping, downloads | Refuse every redirect and non-GET/HEAD request. CSP form-action none, no download permission, no human/model interaction API. Refuse unexpected root navigation, even same origin; declared initial path only. |
| Popups, iframes/srcdoc, dedicated/shared workers and service workers/worklets | CSP sandbox with scripts/same-origin only, frame/worker/object none, service-worker bypass, fresh profile; recursively auto-attach paused and close every extra application target. Browser-wide OS egress denial still applies before an unexpected target is observed. Unsupported nested target becomes a failed check. |
| WebSocket/EventSource streaming | No supported streaming in first subset. Deny via CSP connect policy as applicable, Request-stage policy where observable, and bounded broker content-type/body handling. Any detected attempt fails; process boundary prevents unmediated contact independently. No advertised socket emulation. |
| WebTransport/QUIC, WebRTC/STUN/TURN TCP/UDP, direct sockets, DNS/DoH, prefetch/preconnect/speculation | Process-wide egress isolation is the decisive guard, including IP literals, IPv6 and UDP. Existing flags/CSP/proxy remain defense-in-depth. Request events or global JS replacements are insufficient proof. Count observable attempts without claiming unobserved attempts did not occur. |
| file/chrome/extension/custom schemes, data/blob and permission APIs | No URL override or new target permission; deny non-HTTP navigations; no data/blob script/worker sources; deny permissions/downloads. Allow bounded data images only if explicitly retained. Keep Chrome sandbox enabled. Network isolation alone does not prove host filesystem or arbitrary native-code isolation. |

Broker should strip auth/cookie/proxy/hop-by-hop/reporting/service-worker/location headers and never forward application-controlled browser credentials. Hydrated CSP permits only declared origin scripts (inline bootstrap may be needed for real bundles); no unsafe-eval, worker, frame, object, media, manifest, form or external connect permission. Propose `sandbox allow-scripts allow-same-origin`, default-src none, script-src exact origin plus unsafe-inline for bootstrap, connect-src exact HTTP origin for brokered GET JSON, style/img/font narrowly scoped. This changes application semantics; record the imposed policy in evidence. A same-origin sandbox combining scripts and same-origin is not itself a security boundary. CSP may reject some live application behavior by design.

Ownership checks before/after fetch preserve current protections but do not atomically pin a listening PID across a port-rebind race. The trusted-host boundary must be explicit; existing positive listener proof is not protection against an adversarial privileged peer racing the socket. Do not expand the claim while implementing hydration.

## Proposed contract, lifecycle and evidence

Use discriminated check/evidence unions. Existing strict static rows deserialize unchanged. New hydrated check requires `mode: hydrated`, human-selected `isolation: {kind: linux_netns_v1}` initially, bounded `wait_for` list using existing assertion shapes, `wait_timeout_ms` 100–10000, polling 100ms minimum, and total deadline still at most60s. No raw script field. Reuse resource budgets and assertions. At most10 readiness predicates and25 final assertions; cap DOM traversal/node/text, protocol events10000, total CDP bytes32MiB, in-flight calls32 and diagnostic text40KiB. These are proposed engineering limits, not measured browser requirements.

New evidence: version1, mode hydrated, scriptsEnabled true (not proof arbitrary hydration succeeded), readiness results, final assertion results, configured policy identifier, isolation backend + verified generation, browser product/protocol version, bounded sanitized console/page errors, requests/bytes/violations, exact all-alias heads and existing screenshot metadata. Do not describe script-enabled success as framework hydration correctness: success means the declared DOM readiness/assertions passed under the recorded restricted environment. Old mode static/scriptsExecuted false remains truthful and unchanged. Public evidence contains neither ownership token, pipe handles, profile paths nor raw browser source/arguments. Future stored-result readers accept both union branches without rewriting old rows.

Launch sequence: validate human declaration and backend capability; pin clean heads and owned endpoint; write checked private launch-intent with check/lab/project/generation; create isolated process containment and pipe channels; register exact wrapper identity before launch is released; connect CDP, verify browser version and root target, configure guards/recursive target handling/limits; only then enable scripts and navigate. Keep browser offline emulation secondary if actual backend tests show broker fulfillment works without falsely forcing supported fetch behavior offline. No continuation or direct browser access to service is required.

Wait for declared DOM predicates via DOM-domain queries and bounded polling, not arbitrary page evaluation. Every wait and assertion checks abort/deadline. Preserve broker idle checks but do not use infinite network-idle as readiness (background timers exist). Collect sanitized console primitives without Runtime property expansion/getters or remote-object reads; cap stack/error locations and never capture cookies/storage. Finalize only after broker drain, ownership and heads recheck. Set failed evidence for unexpected navigation/target/transport, limits, revision changes, policy/configuration failure or incomplete cleanup.

Graceful cancellation must close protocol, abort parent fetches, stop exact containment/process tree, drain all tracked work, then remove only checked owned profile paths. Crash recovery requires a durable generation/owner record before execution plus kernel containment lifetime that closes descendants when its owner dies. Recover only exact nonce/process-start identity; never kill arbitrary PIDs. Ambiguous surviving resources are quarantined, evidence preserved and check failed, not adopted as successful. Do not remove ownership proof/profile while an unverified descendant may still be alive. Coordinate persistence/API ownership with root before adding schema; no migrations are implicit in this report.

## Executable phases and file partitions

1. **H0: approve platform boundary and typed contracts.** Supervisor resolves Linux-first capability gate versus separately funded Windows native adapter, bootstrap CSP and deferred cookies/stateful interactions. No implementation starts from an assumption that Windows flags suffice.
2. **H1: independent bounded protocol/capability prerequisite.** One worker owns new `labs/browser-pipe.ts`, `labs/browser-isolation.ts` interface and named unit tests. Frame split/coalescing/NUL handling, oversized/incomplete streams, event/pending caps, abort and fake adapter unavailable paths. No hydrated registration yet; source service/schema files untouched. Another platform worker can own Linux adapter/new native launcher files only after explicit host authorization and prepared Linux fixture. Never concurrently edit browser-process.ts.
3. **H2: schema/broker/DOM integration, serial source ownership.** One worker owns browser-schema/check/network/process plus checks.ts compatibility hunk and dedicated tests; depends on accepted H1 adapter. Add hydrated branch, mode-specific CSP/types, failure diagnostics and declarative waits. Keep artifact code unchanged where possible. No panel/MCP ad hoc evaluation endpoints.
4. **H3: recovery before enablement.** Separate explicitly briefed unit owns private durable launch/recovery integration and any appended migration only after root assigns files. Prove launch-window and killed-owner cleanup, containment reuse refusal and stale generation fencing. H2's runnable hydrated mode remains unavailable until this is integrated.
5. **H4: actual platform acceptance and docs.** Supervisor validates code and real Chrome in isolated fake-service fixture, updates decisions/setup/operations/Labs docs and capability UX, then full checks/package acceptance. Windows lacking a proven adapter must visibly refuse hydrated mode while static remains usable. Model/task verification consumes only normal declared-check results and exact heads.

Acceptance matrix: actual JS module + delayed DOM mutation + same-origin GET JSON pass, while identical static check fails its hydrated-only selector; clean committed heads and screenshot hash retrieval prove the result's revision. Test real nested worker/SW/popup/iframe attempts, foreign HTTP/image/script/form/redirect, WS handshake, EventSource, WebRTC loopback STUN/TURN TCP/UDP, QUIC/WebTransport, IPv4/IPv6 IP literals and resolver paths with local TCP/UDP/DNS sentinels. Require zero foreign accepted connections/datagrams/queries, not merely zero HTTP handlers. Tests should deliberately bypass/disable CDP request interception in a controlled fixture to prove the OS boundary still denies direct network. An unavailable platform API is recorded as unavailable and cannot count as a tested transport. Unknown new transport remains denied by process network isolation.

Also verify timeout on infinite JS/event floods, broker body/request limits, service rebound before request, target setup race, owner crash before/after CDP readiness and while screenshots/fetches run, PID reuse, process descendants and profile cleanup, manager close responsiveness, secret canaries in logs/exception/URLs, stored static evidence compatibility and no new URLs/scripts through model tools. Real netns/AppContainer tests require their actual host primitives; mocks prove interface behavior only. Report fixture PIDs/ports/paths/browser version, immutable heads and cleanup; no paid/external targets.
